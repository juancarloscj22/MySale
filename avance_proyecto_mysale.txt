22. CHECKOUT TRANSACCIONAL Y SEGURIDAD DE STOCK
Se añadió y aplicó la migración 20260929220000_secure_order_checkout.sql. Crea el RPC create_order, restringido a authenticated; valida usuario no bloqueado, datos de entrega, forma/cantidad del carrito, productos activos y stock. Bloquea las filas de producto durante la operación, calcula importes con precios de la base, descuenta stock y guarda cabecera/detalles y datos de entrega de forma atómica. La solicitud incluye una clave idempotente por usuario para que reintentos no creen pedidos duplicados.
Se agregó costo de envío configurable, valor inicial 5.00; el total y moneda se fijan desde configuración/servidor. El checkout requiere sesión y datos de entrega, usa el RPC y ofrece enviar el resumen a WhatsApp tras guardar el pedido. Si falta WhatsApp, el botón de envío queda deshabilitado.
Verificación remota: la migración y firma del RPC existen; SQL confirma EXECUTE denegado a anon y permitido a authenticated. Configuración pública informa envío 5.00, moneda MXN y número WhatsApp aún vacío. Supabase reporta un producto. No se creó pedido de prueba porque no se hizo autenticación de navegador ni se quiso descontar stock real; configurar WhatsApp antes de probar checkout.

23. HISTORIAL Y GESTIÓN DE PEDIDOS REALES
Se conectaron Mis pedidos y el panel Admin → Pedidos a las tablas reales bajo RLS. Los clientes ven únicamente sus pedidos con productos y total; administración/developer puede consultar pedidos y cambiar su estado.
Se añadió y aplicó 20260929223000_secure_order_status_updates.sql: revoca escrituras directas sobre orders/order_items, limita cambio de estado al RPC set_order_status y restaura stock al cancelar. Los pedidos cancelados no se pueden reabrir. Verificaciones remotas confirmaron las dos migraciones, RPCs existentes, permisos anon/authenticated adecuados y sin permiso de UPDATE directo sobre orders; REST para orders, order_items, products y site_settings respondió HTTP 200.
Lint pasó; build pasó con la advertencia existente de bundle de Vite >500 kB. No se efectuó pedido de prueba real para no consumir stock y porque WhatsApp de tienda aún no está configurado.
La migración 20260929224500_guard_order_cancellation_stock.sql limita la restauración de stock a pedidos que todavía no estén en tránsito o completados, para evitar reponer productos posiblemente entregados; un pedido completado tampoco puede modificarse.
El checkout incluye hora preferida de entrega (opcional) y selector de medio de pago: efectivo al recibir, transferencia bancaria o tarjeta al recibir. La hora y método se persisten con el pedido, aparecen en Mis pedidos y en administración, y se añaden al mensaje de WhatsApp. El pago solo se registra como preferencia; no hay procesamiento en línea.

El registro solicita nombre completo y teléfono. El checkout usa automáticamente ambos datos del perfil y ya no los vuelve a pedir en los datos de entrega. Se añadió Mi cuenta para corregirlos en perfiles existentes, con permisos limitados a editar únicamente nombre y teléfono propios.
Tras guardar un pedido, checkout muestra una pantalla de confirmación; WhatsApp se abre solo al pulsar el enlace y en una pestaña nueva, sin abandonar ni cerrar la tienda.
Si el medio elegido es efectivo, el checkout permite indicar si el cliente requiere cambio. Esta preferencia se guarda con el pedido y aparece en Mis pedidos, administración y el mensaje de WhatsApp.
El checkout también solicita indicar si el domicilio está en zona aledaña. Si la respuesta es sí, aplica el costo de envío configurado; si es no, el envío cuesta cero. La preferencia se persiste con el pedido, se calcula en el RPC transaccional del servidor y se muestra en historial, administración y WhatsApp.

28. ACCIONES SEGURAS DE GESTIÓN DE USUARIOS
La tabla Admin → Usuarios muestra acciones de bloquear/desbloquear y eliminar únicamente para perfil developer. Estas operaciones se ejecutan por la Edge Function manage-user, desplegada con verificación JWT y validación del rol developer en servidor. El bloqueo actualiza el estado de perfil y aplica/quita la prohibición de acceso en Supabase Auth; si la actualización del perfil falla, intenta revertir el cambio de Auth. La eliminación permanente usa Auth Admin API y conserva los pedidos históricos (user_id queda nulo). Se impide actuar sobre la propia cuenta o cuentas developer.
